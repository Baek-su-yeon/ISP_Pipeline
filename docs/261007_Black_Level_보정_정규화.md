# 261007 1단계 Black Level 보정·정규화 회고

Oct 7, 2026 · @돌침대

## 요약

raw 정수값에서 화소별 기준값을 빼고 `(WL − 기준값)`으로 나눠 0\~1 float 이미지를 만들었다. a0001, a0005 두 장 모두 검증을 통과해 1단계가 끝났다.

- **기준값**: 공통값(`black`) + 색별 값(`cblack[COLOR()]`) + 위치 패턴 값(`cblack[6 + idx]`). 2×2 표를 먼저 출력해 확인한 뒤 전체 반복문에 넣었다.
- **검증**: a0001은 OpenCV `convertTo` 결과와 610만 화소가 모두 같았다. a0005는 0-2 대비 최대 차이 10으로, 기준값 127을 실제로 뺐음을 숫자로 확인했다. 포화 화소 537,338개가 모두 정확히 1.0이 됐다.
- **가장 많이 배운 것**: 이번 단계의 버그 대부분은 a0001에서 결과가 맞아 보이는 버그였다. 값 대신 인덱스를 출력하고, 조건이 다른 두 사진으로 확인해야 잡혔다.
- **코드**: `src/test.cpp`.

## 진행 순서

기준값 계산을 2×2 표로 먼저 검증하고, 그다음 전체 이미지로 넓혔다. 한 번에 하나만 바꿔서 어디가 틀렸는지 바로 보이게 했다.

1. 1단계의 목적 정리: 0 = 빛 없음, 1 = 포화인 선형 값 만들기
2. `black`과 `cblack`의 구조 정리 (공통값, 색별 값, 위치 패턴)
3. 2×2 기준값 표 출력: 공통값 + 색별 값 → a0001 `0 0 / 0 0`, a0005 `127 128 / 127 127`
4. 위치 패턴 크기 출력과 패턴 값 추가 → 인덱스(`6 + idx`)를 출력해 a0001이 칸 6만 읽는지 확인
5. 전체 반복문으로 확장: 여백 인덱스, float 계산, 0\~1 자르기, `CV_32F` Mat에 저장
6. 최솟값·최댓값 확인
7. 8비트로 저장하고 0-2 이미지(`real.png`, `real_usingfunc.png`)와 비교
8. a0005로 기준값 빼기와 포화 화소 1.0 확인

## 겪은 버그와 해결

고친 버그 열 개 중 다섯 개는 출력이 기대값과 같아서 실행 결과만으로는 잡을 수 없었다. a0001은 Black Level과 패턴 값이 모두 0이라, 잘못된 칸을 읽어도 0이 나오기 때문이다.

| 버그 | 결과가 맞아 보였나 | 원인 | 해결 |
| --- | --- | --- | --- |
| 기준값을 "패턴이 없을 때만" 계산 | 아니요. a0001 표가 비어 나옴 | 조건 `!patternR && !patternC`는 "둘 다 0". 공통값과 색별 값까지 그 분기 안에 넣음 | 공통값 + 색별 값은 항상, 패턴 값만 `patternR && patternC`일 때 추가 |
| 패턴 크기 출력이 4번 | 아니요 | 사진에 하나뿐인 값을 2×2 반복문 안에서 읽음 | 반복문 밖으로 |
| 패턴 인덱스에 `COLOR()` 사용 | **예** | 위치 기준 표를 색 번호로 찾음. a0001은 칸 6 대신 8을 읽음 | 패턴 안 (행, 열)을 1차원으로 펼친 값 사용 |
| 패턴 인덱스 `r * patternR + c` | **예** | 나머지(`%`) 없음, 곱하는 값이 열 수가 아닌 행 수. a0001은 칸 6, 7, 7, 8을 읽음 | `(r % 행 수) * 열 수 + (c % 열 수)` |
| `colors` 표 `me == 'G'` → 2 | **예**에 가까움 | 0-3 코드에서 옮기며 `'B'`를 `'G'`로 씀 | 1단계에서는 `colors` 표를 쓰지 않으므로 제거 |
| `cblack[bases[r % 2][c % 2]]` | **예** | 이미 기준값인 127, 128을 다시 인덱스로 씀. `cblack[127]`이 0이라 a0005의 G가 128이 아닌 127로 계산 | `base = bases[r % 2][c % 2]` |
| `(raw × 255 / WL) − base` | 아니요 | 8비트 표시용 변환과 raw 단위 기준값을 섞음 | `(raw − base) / (WL − base)` |
| `int / int` 나눗셈 | **예** (a0005) | 소수점이 버려져 거의 다 0, 포화만 1. a0005는 최소 0, 최대 1로 기대값과 같았음 | 나누기 전에 `static_cast<float>` |
| `convertTo(..., 255.0 / WL)` | 아니요. 새까만 이미지 | 이미 0\~1인 값을 WL로 한 번 더 나눔 | 배율 `255.0` |
| 저장 이름 `"normImg"` | 아니요 | 확장자가 없어 저장 형식을 정할 수 없음 | `"normImg.png"` |

**잡은 방법**

- **값 대신 인덱스 출력**: 패턴 인덱스 버그 두 개는 `6 + idx`를 출력해서 보였다. 1×1 패턴이라면 네 칸 모두 6이어야 한다.
- **조건이 다른 사진으로 확인**: a0001에서는 0이라 숨는 버그가 a0005에서는 숫자로 드러난다. 정수 나눗셈은 반대로 a0001의 최댓값(0이 나옴)에서 드러났다.
- **계산식으로 기대값을 먼저 적기**: a0001 최대 3821/4095 ≈ 0.933, a0005 최대 차이 127/3398 × 255 ≈ 9.5. 기대값이 있어야 맞는지 판단할 수 있다.

**C++에서 주의할 점**

- `black`, `cblack[]`, `raw_image`는 모두 unsigned. unsigned끼리 빼서 음수가 되면 40억 근처의 큰 수가 된다.
- `!a && !b`(둘 다 0)의 반대는 "하나라도 0이 아님"이다. "둘 다 0이 아님"은 `a && b`로 직접 쓴다.
- `cv::imread`는 실패해도 에러 없이 빈 Mat을 돌려준다. `empty()`를 확인한다.

## 검증 결과

두 사진 모두 기대값과 일치했다. a0001은 계산 경로 전체를, a0005는 기준값 빼기와 포화 처리를 검증한다.

| 확인 | a0001 | a0005 | 판정 |
| --- | --- | --- | --- |
| 패턴 크기 | 1 × 1 | 0 × 0 | 메타데이터와 일치 |
| 기준값 2×2 | 0 0 / 0 0 | 127 128 / 127 127 | G만 128, G2는 127 |
| 최솟값 | 0.000488 (raw 2) | 0 (기준값 아래 화소를 자름) | 정상 |
| 최댓값 | 0.933089 (3821/4095) | 1 | 0-4 최댓값과 일치 |
| vs `real.png` (버림) | 최대 1, 48.5% 다름 | — | 버림 vs 반올림 차이 |
| vs `real_usingfunc.png` (반올림) | 최대 0, 0% 다름 | 최대 10 | a0005는 기준값을 뺀 만큼 차이 |
| 정확히 1.0인 화소 | 0 | 537,338 | 0-4 포화 비율로 계산한 약 537,300과 일치 |

- **a0001 최대 차이 0**: 기준값 0이라 이번 계산이 `raw / 4095 × 255` 반올림과 같다. 610만 화소가 OpenCV 결과와 하나도 다르지 않으니 인덱스, float 계산, 자르기, 8비트 변환이 모두 맞다.
- **a0005 최대 차이 10**: 0-2는 raw 127을 약 9.5로 표시했고, 이번에는 0이 된다. 차이는 어두운 곳에서 가장 크고 포화 화소에서 0이 된다. 최대 차이가 127/3398 × 255와 맞으니 기준값을 실제로 뺐다.
- **a0005 포화 화소**: `(3398 − base) / (3398 − base)`라 기준값이 127이든 128이든 정확히 1.0이 된다.
- **눈으로는 거의 같음**: 차이가 최대 4%이고 어두운 곳에만 있어, 감마 전 선형 이미지에서는 잘 보이지 않는다. 감마가 어두운 값을 끌어올리는 4단계 이후에 드러날 것이다(실험 2에서 확인).

## 질문하며 정리한 개념

### 1단계는 무엇을 위해 하나

센서값을 빛의 양에 비례하는, 카메라와 무관한 0\~1 값으로 바꾼다.

- **Black Level 빼기**: 0을 "빛 없음"으로 맞춘다. 빼지 않으면 WB 이득이 고정값에도 곱해져 어두운 곳에 색이 끼고, 감마 뒤에 검정이 회색으로 뜬다.
- **정규화**: 1을 "포화"로 맞춘다. WL이 카메라마다 달라도 이후 단계 코드가 카메라를 몰라도 된다.
- 1단계가 틀리면 에러 없이 뒤 단계의 색과 밝기만 조용히 틀어진다.

### black과 cblack

| 부분 | 위치 | 기준 |
| --- | --- | --- |
| 공통값 | `black` | 모든 화소 |
| 색별 값 | `cblack[0..3]` | LibRaw 색 번호 (R, G, B, G2) |
| 위치 패턴 크기 | `cblack[4]`, `cblack[5]` | 행 수, 열 수. 0이면 없음 |
| 위치 패턴 값 | `cblack[6]~` | 화소 위치 `(r % 행 수, c % 열 수)` |

세 값은 더해서 기준값 하나로 만든 뒤 한 번 뺀다. a0005의 G는 "127을 빼고 1을 또 빼는" 게 아니라 128을 한 번 뺀다.

### 위치 패턴과 Bayer 패턴

|  | Bayer 패턴 | Black Level 위치 패턴 |
| --- | --- | --- |
| 표에 든 것 | 위치별 색 필터 | 위치별 기준값 숫자 |
| 크기 | 항상 2×2 | 1×1, 2×2, 1×N 등 |
| 읽는 곳 | `filters`, `COLOR()` | `cblack[4]~` |

센서가 열이나 행마다 다른 읽기 회로를 쓰면 색과 무관하게 위치별로 기준값이 달라질 수 있다. 그래서 위치 기준 표가 따로 있다. DNG 규격에 기준값을 반복 표로 적는 방식이 있고, FiveK의 Nikon 사진은 1×1 표로 기록돼 있다. 1×1은 사실상 공통값이다.

### 왜 둘 다 0이 아닐 때만, 왜 6을 더하나

- 0은 "패턴 없음"이다. 또 `r % 0`은 0으로 나누는 계산이라 프로그램이 죽는다.
- `cblack`은 1차원 배열이고 0\~5번 칸은 이미 색별 값과 크기가 쓴다. 패턴 표는 6번부터 행 단위로 펼쳐 저장돼 있다.
- 패턴 안 (i, j)의 칸은 `6 + i × 열 수 + j`. `raw_image` 인덱스와 같은 구조다.

## 배운 점과 다음 단계

**배운 점**

- 결과가 맞는다고 계산이 맞는 건 아니다. 값이 0인 데이터에서는 어느 칸을 읽어도 0이 나온다.
- 번호에는 출처가 있다. `cblack`, `cam_mul`은 LibRaw 색 번호, 채널 분리와 Demosaic은 내 `colors` 표 번호다. 지금은 두 번호가 같아 섞어도 티가 안 난다.
- 단위를 섞지 않는다. 8비트 표시용 `× 255 / WL`과 raw 단위 기준값은 같은 식에 들어갈 수 없다.
- 기대값을 계산으로 먼저 적어 두면 결과를 바로 판정할 수 있다.
- Black Level의 효과는 선형 이미지에서 잘 보이지 않는다. 감마 이후에 드러난다. README와 면접에서 쓸 관찰이다.
