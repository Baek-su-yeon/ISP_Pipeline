# a0001.dng 메타데이터 해석 — 각 값의 의미와 확인한 이유

ISP 각 단계는 "이 센서가 어떻게 기록했는가"를 알아야 계산할 수 있다. 메타데이터는 그 기록 방식의 설명서이고, 처리를 시작하기 전에 확인해야 이후 단계가 틀어지지 않는다.

| 항목 | 값 | 의미 | 쓰는 단계 |
| --- | --- | --- | --- |
| 카메라 | Nikon D70 | 데이터를 만든 센서 | 사진 간 차이 해석 |

## 카메라 정보: Nikon D70

이 데이터를 만든 센서가 무엇인지 알려준다. 처리 자체에 직접 쓰는 값은 아니지만, 사진마다 결과가 다를 때 원인을 해석하는 기준이 된다.

- **의미**: 제조사(`idata.make`)와 모델(`idata.model`). 3040 × 2014 ≈ 610만 화소 센서
- **왜 확인했나**: FiveK는 여러 사진가가 서로 다른 카메라로 찍은 데이터라, 사진마다 Bayer 패턴, Black Level, White Level이 다를 수 있다. 같은 코드를 돌렸는데 사진마다 색이 이상하게 나오면 카메라가 다른지부터 본다
- **파이프라인에 미치는 영향**: 코드에 "BGGR", "4095" 같은 값을 박아 넣지 않고 매번 메타데이터에서 읽어야 하는 이유. 다른 카메라 사진(0005, 0078 등)에서 값이 바뀌어도 코드가 그대로 동작해야 한다

## Bayer 패턴: BGGR

센서 화소 하나는 한 색의 빛만 잰다. BGGR은 맨 왼쪽 위 2×2 칸이 이렇게 배치되고, 이 블록이 이미지 전체에 반복된다는 뜻이다.

```
        열 0(짝수)  열 1(홀수)
행 0(짝수)    B          G
행 1(홀수)    G          R
```

| 위치 | 색 |
| --- | --- |
| 짝수 행, 짝수 열 | B |
| 짝수 행, 홀수 열 | G |
| 홀수 행, 짝수 열 | G |
| 홀수 행, 홀수 열 | R |

- **의미**: 출력은 `COLOR(r, c)`로 2×2 네 위치의 색 번호를 얻고, `cdesc`로 글자로 바꾼 것. 숫자 `filters`(505290270)는 이 배치를 비트로 압축한 값이다
- **왜 확인했나**: 이후 모든 단계가 "이 화소가 무슨 색인가"에서 출발한다. 채널 분리는 이 표대로 화소를 나누고, WB는 화소 색에 맞는 이득을 곱하고, Demosaic은 빠진 두 색을 어느 이웃에서 가져올지 이 배치로 정한다
- **틀리면**: R과 B를 바꿔 읽으면 사진 전체가 파랗거나 주황색으로 뒤집힌다. 에러 없이 "색만 이상한" 결과가 나와서 원인 찾기가 어렵다. 처리 전에 한 번 출력해 두는 이유다
- **주의**: 이미지를 홀수 화소만큼 잘라내면 패턴의 시작점이 바뀐다(BGGR → GBRG 등). 자를 때는 2의 배수로 자르거나 `COLOR()`로 다시 확인한다

## 크기와 여백: 3040 × 2014, 여백 0

Raw 크기는 메모리에 올라온 배열의 크기, 실제 크기는 그중 사진으로 쓰는 영역, 여백은 그 영역이 배열 어디서 시작하는지다. 이 사진은 세 값이 모두 같아서 가장 단순한 경우다.

- **의미**
  - `raw_width`, `raw_height`: `raw_image` 배열 전체 크기
  - `width`, `height`: 테두리를 뺀 유효 영역 크기
  - `top_margin`, `left_margin`: 유효 영역의 시작 위치
- **왜 확인했나**: `raw_image`는 2차원 표가 아니라 화소값이 한 줄로 늘어선 1차원 배열이다. (행, 열) 위치의 값을 꺼내려면 "한 줄에 몇 개씩 놓였는가"를 알아야 한다. 그 기준이 `raw_width`이고, 유효 영역 좌표를 배열 좌표로 옮길 때 여백을 더한다

```
유효 영역 (r, c)의 값 = raw_image[(r + top_margin) * raw_width + (c + left_margin)]
이 사진: raw_image[r * 3040 + c]
```

- **다른 카메라에서는**: 테두리에 빛을 가린 화소(광학적 검정 영역)가 있어 여백이 0이 아닌 경우가 많다. 이 영역은 Black Level 추정에 쓰이기도 한다. 여백을 무시하면 이미지가 어긋나거나 검은 띠가 섞인다
- **2의 배수인지**: 3040과 2014 모두 짝수라 2×2 블록이 남는 화소 없이 딱 맞는다. 채널 분리하면 각 채널은 1520 × 1007이 되고, G는 두 개(G1, G2)라 R·G1·G2·B 네 장이 나온다

## Black Level: 0 (채널별 0 0 0 0)

빛이 전혀 없을 때 센서가 기록하는 기본값이다. 이 사진은 0이라 뺄 값이 없다.

- **의미**: 많은 센서는 노이즈가 0 아래로 잘려 사라지지 않도록 일부러 양수 기준값(offset)을 더해 기록한다. LibRaw는 이를 공통값(`black`)과 채널별 추가값(`cblack[0..3]`)으로 나눠 저장한다. 실제 기준값은 둘을 더한 것
- **왜 확인했나**: 모든 계산은 "0 = 빛 없음, 값은 빛의 양에 비례"를 전제로 한다. 기준값을 빼지 않으면
  - 어두운 부분이 들뜨고 대비가 떨어진다(뿌옇게 보임)
  - WB 단계에서 기준값까지 채널별 이득이 곱해져 어두운 부분에 색이 낀다
- **이 사진에서 0인 이유**: 카메라나 DNG 변환 과정에서 이미 빼 둔 것으로 보인다. raw-identify 결과와 대조해 확정할 것
- **구현 방침**: 이 사진은 0이어도, 다른 사진은 값이 있을 수 있으므로 Black Level을 빼는 코드는 그대로 넣는다. 0이면 결과에 영향이 없을 뿐이다

```
정규화 값 = (화소값 − black) / (white − black)
이 사진: 화소값 / 4095
```

## White Level: 4095

센서가 기록할 수 있는 최댓값이다. 4095 = 2¹² − 1이므로 이 센서는 화소값을 12비트(0\~4095)로 기록한다.

- **의미**: LibRaw에서는 `color.maximum`. 빛이 이 이상 들어와도 값은 4095에서 멈춘다(포화)
- **왜 확인했나**
  - **정규화 기준**: 1단계에서 화소값을 0\~1 범위로 바꿀 때 나누는 값. 카메라마다 비트 수가 달라(12비트, 14비트 등) 이 값으로 나눠야 이후 단계가 카메라와 무관하게 같은 기준으로 동작한다
  - **포화 판정**: 값이 4095인 화소는 실제 밝기를 잃은 화소다. 밝은 하늘이나 조명처럼 하얗게 날아간 부분
- **포화가 문제 되는 곳**
  - WB: 포화된 화소에 R·B 이득을 곱하면 원래 흰색이던 부분이 분홍·자주색으로 변할 수 있다. 하이라이트 처리가 필요한 이유
  - 어둡고 강한 불빛이 있는 사진(0078, 0192)에서 특히 눈에 띌 것
- **저장할 때**: 결과를 8비트(0\~255) 이미지로 저장하면 12비트 정보가 줄어든다. 중간 계산은 실수(float)로 하고 마지막에만 8비트로 바꾸는 게 좋다

## WB 계수: 2.12891, 1, 1.54687, 0

촬영할 때 카메라가 "이 조명에서 흰색이 흰색으로 보이려면 채널별로 이만큼 곱하라"고 기록해 둔 값이다(As Shot WB).

- **순서**: `cam_mul[4]`는 Bayer 위치 순서가 아니라 색 순서다. `cdesc`(보통 "RGBG") 순서를 따른다

| 인덱스 | 색 | 값 |
| --- | --- | --- |
| 0 | R | 2.12891 |
| 1 | G | 1 |
| 2 | B | 1.54687 |
| 3 | G2 | 0 |

- **의미**
  - G를 1로 두고 R, B를 상대값으로 표현한 것
  - R 이득이 가장 크다 → 이 촬영 조건에서 센서가 R을 상대적으로 약하게 받았다는 뜻. 센서는 보통 G에 가장 민감하고, Bayer에 G가 두 배 많아 G가 기준이 된다
  - G2의 0은 "따로 없음, G와 같음"이라는 표시로 읽는다
- **왜 확인했나**
  - **WB 첫 구현의 기준값**: 2단계에서 처음엔 이 값을 그대로 곱해 결과를 확인하고, 다음에 Gray World를 직접 구현해 이 값과 비교한다. "카메라가 고른 값"이 정답 역할을 한다
  - **색 → 이득 매핑**: 화소 색은 `COLOR(r, c)`로 얻고, 그 번호로 `cam_mul`을 고른다. BGGR이라고 해서 cam\_mul 순서가 B, G, G, R인 게 아니다
- **함정**: `COLOR()`가 두 번째 G에 3을 돌려주면 `cam_mul[3]` = 0이 곱해져 G2 화소가 전부 검게 된다. G2에는 `cam_mul[1]`을 쓰거나, 0이면 G 값으로 바꿔 쓰는 처리가 필요하다. 채널 분리 결과에서 G2가 검게 나오는지 확인하면 이 처리를 검증할 수 있다

## 이 값들로 정해진 것과 남은 확인

메타데이터를 확인한 덕분에 다음 단계의 계산식과 주의점이 정해졌다.

**정해진 것**

- 화소 접근: `raw_image[r * 3040 + c]` (여백 0). 코드에는 숫자 대신 `raw_width`, 여백 변수를 쓴다
- 채널 분리: BGGR 기준 2×2 위치로 나누면 각 채널 1520 × 1007
- 1단계 정규화: `(값 − black) / (white − black)`, 이 사진은 `값 / 4095`
- 2단계 WB 기준값: R 2.129, G 1, B 1.547. G2는 G 값 사용
- 코드에 카메라별 값을 박아 넣지 않고 매번 메타데이터에서 읽음

**남은 확인**

- [ ] raw-identify로 Black Level 0, WB 계수 대조
- [ ] 다른 사진(0005, 0078)의 메타데이터도 출력해 카메라별 차이 확인
- [ ] 채널 분리 결과에서 G1, G2가 비슷한 밝기인지 확인 (G2가 검으면 매핑 오류)
- [ ] 4095에 닿은 화소가 얼마나 되는지 확인 (포화 영역)
