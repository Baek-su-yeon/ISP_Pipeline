## 요약

`WBClip`(Bayer 1채널)을 Bilinear로 보간해 화소마다 R·G·B 세 값을 가진 `Demosaic`(`CV_32FC3`)을 만들었다. a0001, a0005 두 장 모두 이웃 좌표와 채널 평균이 기대값과 일치해 3단계가 끝났다.

- **방식**: 분기 4개 대신, 이웃 8칸을 돌며 `colors` 번호로 색별로 모아 평균. G\_R·G\_B는 G 하나로 합치고, 자기 색은 자기 값만 쓴다.
- **가장자리**: 테두리 버리기로 먼저 완성한 뒤 반사(reflect)로 바꿨다. 반사는 홀짝이 유지돼 같은 색 화소를 읽는다.
- **검증**: G 위치에서 대각선(출력 번호 짝수)이 건너뛰어짐, a0005는 같은 좌표에서 색 번호만 0↔2로 바뀜. Demosaic 채널 평균이 `WBClip` Bayer 채널 평균과 소수 넷째 자리까지 일치.
- **가장 많이 배운 것**: 반복문 범위가 반사 코드를 아예 안 부르면 버그가 숨는다. 고친 코드가 실제로 실행되는 화소(모서리)를 직접 찍어 봐야 한다.
- **코드**: `src/test.cpp`.

## 시작 전 정리

코드 전에 `colors` 번호별로 채울 색과 이웃을 표로 정했다. a0001 왼쪽 위 4×4를 그려 놓고 화소 하나씩 오프셋을 대조했다.

```
      c=0  c=1  c=2  c=3
r=0    B    G    B    G
r=1    G    R    G    R
r=2    B    G    B    G
r=3    G    R    G    R
```

| `colors` | 자기 색 | 채울 색 ← 이웃 | 확인한 화소 (a0001) |
| --- | --- | --- | --- |
| 0 R | R | G ← 상하좌우 4개 / B ← 대각선 4개 | `(1, 1)` |
| 1 G\_R | G | R ← 좌우 2개 / B ← 상하 2개 | `(1, 2)` |
| 2 B | B | G ← 상하좌우 4개 / R ← 대각선 4개 | `(2, 2)` |
| 3 G\_B | G | R ← 상하 2개 / B ← 좌우 2개 | `(2, 1)` |

- 이 표는 BGGR·RGGB 모두에 그대로 쓴다. 패턴 차이는 `colors[r % 2][c % 2]`가 흡수한다.
- G\_R의 정의("같은 행 옆 칸이 R인 G")가 곧 "R은 좌우, B는 상하"다. 이 정의를 놓치면 방향이 뒤집힌다.
- 확인 화소는 가장자리를 피해 골랐다. 이웃이 전부 그림 안에 있어야 대조가 쉽다.

**가장자리 처리 결정**

| 방법 | 내용 | 판단 |
| --- | --- | --- |
| 테두리 버리기 | 반복문을 `1 ~ H-2`로, 바깥 1화소는 0 | 가장 간단. 먼저 완성 |
| 단순 clamp | 밖으로 나간 좌표를 `0` 또는 `H-1`로 당김 | **색이 틀림**. `(0,0)` B의 `(-1,-1)` → `(0,0)` = B 값을 R로 씀 |
| 반사 | `-1 → 1`, `H → H-2` | 2칸 간격 반사라 홀짝 유지 → 같은 색을 읽음. 테두리 버리기 뒤 구현 |

**타입 결정**: 결과는 `CV_32FC3`, 내부 채널 순서는 RGB(`[0]` R). OpenCV 저장이 BGR이라 저장 직전에만 `cvtColor(RGB2BGR)`. 5단계 CCM이 RGB 순서 행렬이라 내부를 RGB로 두는 편이 덜 헷갈린다.

## 겪은 버그와 해결

이번에도 "컴파일은 되는데 값만 틀리는" 종류가 핵심이었다. 특히 반복문 범위 때문에 반사 버그가 결과에 드러나지 않았다.

| 버그 | 결과가 맞아 보였나 | 원인 | 해결 |
| --- | --- | --- | --- |
| G\_R의 R·B 방향을 반대로 적음 | — (표 단계) | G\_R 정의(같은 행에 R)를 안 떠올림 | 그림에서 해당 칸 색을 직접 확인 |
| 분기 안에 `for (i < 3)` | — | 세 색이 각기 다른 이웃에서 옴 | 반복 대신 색별 식, 결과는 한 번만 대입 |
| G를 칸 1·3으로 따로 모음 | **예** (R·B 위치) | R 위치의 G 4개가 좌우 2 / 상하 2로 쪼개짐 | 모을 때 3을 1로 합쳐 R·G·B 3칸만 사용 |
| G 위치에서 칸 3의 `count` 0 | 아니요. NaN | 대각선 G를 건너뛰어 아무것도 안 모임 | 위와 같이 3칸으로 줄여 해결 |
| `const int* colors`에 `[][]` | 아니요. 컴파일 에러 | 2차원 배열을 포인터로 받음 | `const int (&colors)[2][2]` |
| 화소마다 `std::vector` 반환 | 예 (느리기만 함) | 수백만 번 힙 할당 | `cv::Vec3f` 반환 |
| `Demosaic[i].at<cv::Vec1f>` | 아니요. 컴파일 에러 | Mat은 `[i]` 접근 불가, 3채널은 `Vec3f` | `.at<cv::Vec3f>(r, c)`에 한 번에 |
| 반사 함수인데 반복문은 `1 ~ H-2` | **예** | 가장자리를 아예 안 돌려 반사 코드가 한 번도 실행 안 됨 | 범위 `0 ~ H-1` |
| 아래·오른쪽 반사를 `rr *= -1` | 실행 시 범위 밖 읽기 | `rr = rows` → `-rows`. `.at`은 범위 검사 안 함 | 아래·오른쪽은 `rr -= 2` (1칸 이웃 한정) |
| 주석 속 반복문 범위 `r < realH - 1` | **예** | 마지막 행·열이 빠짐 | `r < realH`, `c < realW` |
| 함수 안 검증용 `cout` | — (켜기 전 발견) | 전체 실행 시 수천만 줄 출력 | 검증 뒤 주석 처리 |

## 질문하며 정리한 개념

### Demosaic, 이웃, 오프셋

Bayer 화소는 색이 하나뿐이다. Demosaic은 없는 두 색을 채운다. Bilinear는 바로 붙은 8칸 중 그 색을 가진 화소의 평균을 쓴다. 이 주변 화소가 이웃이고, 자기 위치에서 떨어진 칸 수 `(dr, dc)`가 오프셋이다. 위는 `(-1, 0)`, 오른쪽 아래 대각선은 `(+1, +1)`.

### 단계마다 타입이 바뀌는 이유

OpenCV 타입은 자료형 + 채널 수다. `CV_32FC3` = 32비트 float × 3채널.

| 단계 | 자료형 | 채널 | 이유 |
| --- | --- | --- | --- |
| RAW | 16비트 정수 | 1 | 센서가 정수로 줌 |
| 1·2단계 | 32F | C1 | 정규화로 소수가 생김 |
| 3단계 | 32F | C3 | 화소마다 R·G·B 세 값 |
| 저장 | 8U | C1 / C3 | png용 0\~255 |

자료형은 한 번(정수 → float), 채널 수는 한 번(1 → 3) 바뀌었다. 접근 타입도 따라서 `float` → `cv::Vec3f`.

### clamp가 아니라 반사인 이유

단순 clamp는 밖으로 나간 좌표를 가장 가까운 안쪽으로 당긴다. 일반 이미지에선 괜찮지만 Bayer에선 당긴 칸의 색이 다르다. `(0, 0)` B의 R 이웃 `(-1, -1)` → `(0, 0)`은 B다. 반사는 경계 화소를 거울로 삼아 2칸 간격으로 접으므로 홀짝이 유지돼 같은 색을 읽는다.

### `-1 % 2`는 `-1`

C++의 `%`는 음수에서 음수를 돌려준다. `colors[rr % 2]`에 음수 `rr`이 들어가면 배열 밖을 읽는다. 그래서 반사를 `colors` 조회보다 먼저 한다.

### 기대값은 실제 입력 기준으로

Demosaic 입력이 `WBClip`이면 기대값도 `WBClip`에서 계산한다. `WBImg` 평균은 잘리기 전 값이라 비교 대상이 아니다. a0001은 클리핑이 없어 두 값이 같았고, a0005에서만 차이가 드러났다.

### WBClip을 하는 이유

포화 영역은 R·G·B가 모두 1.0(흰색에 가까움)이다. WB 후 a0005는 R 2.05, G 1.0, B 1.37이 되어 흰색이 분홍빛으로 틀어진다. 1에서 자르면 다시 흰색이 되지만 그 영역의 밝기 차이는 사라진다. 이 득실 비교가 실험 3이고, 감마 뒤에 한다.

## 배운 점과 다음 단계

**배운 점**

- 고친 코드가 실제로 실행되는지 먼저 확인한다. 반복문 범위가 가장자리를 안 돌면 반사 코드는 맞든 틀리든 결과가 같다.
- 검증용 화소는 확인하려는 코드가 동작하는 곳으로 고른다. R 화소 `(1,1)`은 건너뛰기가 없어 G 위치를 따로 봐야 했다.
- 같은 좌표를 두 패턴(a0001, a0005)에서 찍으면 패턴 처리가 맞는지 한 번에 보인다.
- 분기를 하드코딩하는 대신 표(`colors`)에서 규칙이 나오게 하면 패턴이 바뀌어도 코드가 그대로다.
- 기대값은 실제 입력 기준으로 계산한다. 리뷰 쪽 기대값도 틀릴 수 있다.
- 이웃 읽기를 함수 하나에 모아 두어, 가장자리 처리를 바꿀 때 몇 줄만 고쳤다.
