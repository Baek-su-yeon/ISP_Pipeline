# 261004 WSL C++ 개발 환경 구축

Oct 4, 2026 · @돌침대

## 환경 개요

WSL Ubuntu에 LibRaw와 OpenCV를 설치하고, CMake로 둘을 불러오는 테스트 프로그램(check\_env)을 빌드·실행하는 데 성공했다. VSCode의 헤더 인식 문제까지 해결해 C++ 개발 환경 구축을 마쳤다.

| 항목 | 내용 |
| --- | --- |
| 호스트 OS | Windows (주 개발 환경) |
| 개발 OS | WSL Ubuntu 24.04, PowerShell로 접속 |
| 편집기 | VSCode (WSL 원격 연결), WSL 쪽 익스텐션: C/C++, Python, Pylance, Python Debugger, Python Environments |
| 레포 | `~/projects/ISP_Pipeline` (GitHub에서 SSH로 clone) |
| 컴파일러 | g++ 13.3.0 |
| 빌드 도구 | CMake 3.28.3 |
| RAW 읽기 | LibRaw 0.21.2 |
| 영상 저장·배열 | OpenCV 4.6.0 |
| 설치 방식 | apt 전역 설치 |

## 진행 순서

레포 준비 → 패키지 설치 → 설치 확인 → 빌드 테스트 → 편집기 설정 순으로 진행했다. 중간에 conda 환경과 sudo 비밀번호 문제를 처리했다.

1. `~/projects`에 ISP\_Pipeline 레포를 clone하고 `code .`로 VSCode 연결
2. WSL 쪽에 C/C++, Python 익스텐션 설치
3. conda base 비활성화 (C++ 빌드 시 라이브러리 경로 섞임 방지)
4. apt로 빌드 도구, LibRaw, OpenCV 설치
5. 버전 확인 명령으로 설치 검증
6. 레포에 build, data, output 폴더 생성, .gitignore 작성
7. CMakeLists.txt와 src/check\_env.cpp 작성
8. cmake → make → 실행으로 빌드 테스트 성공
9. VSCode에서 OpenCV 헤더를 못 찾는 경고 발생 → compile\_commands.json + c\_cpp\_properties.json으로 해결

## 패키지 설치

세 줄로 컴파일 도구와 두 라이브러리를 설치했다.

```bash
sudo apt update
sudo apt install -y build-essential cmake pkg-config gdb
sudo apt install -y libraw-dev libopencv-dev
```

| 요소 | 의미 |
| --- | --- |
| `sudo` | 관리자 권한으로 실행 |
| `apt update` | 설치 가능한 패키지 목록을 최신으로 받아옴. 설치된 프로그램을 올리는 건 `apt upgrade`로 별개 |
| `-y` | "계속할까요? \[Y/n\]" 질문에 미리 yes로 답함 |
| build-essential | C/C++ 컴파일 기본 묶음. g++, make, 표준 헤더 |
| cmake | CMakeLists.txt를 읽어 make가 실행할 빌드 파일을 만드는 빌드 설정 도구 |
| pkg-config | 설치된 라이브러리의 헤더·라이브러리 파일 위치를 알려주는 도구 |
| gdb | 디버거. VSCode 중단점 디버깅이 내부적으로 사용 |
| libraw-dev | LibRaw. `-dev`는 코드에서 include할 헤더와 링크용 파일까지 포함한다는 뜻 |
| libopencv-dev | OpenCV 개발용 패키지 |

설치 확인 명령과 결과:

```bash
g++ --version                  # 13.3.0
cmake --version                # 3.28.3
pkg-config --modversion libraw # 0.21.2
pkg-config --modversion opencv4 # 4.6.0
```

## 빌드 구성

CMakeLists.txt는 레포 최상단, 소스는 src/에 둔다. build 폴더 안에서 `cmake ..`를 치면 한 단계 위의 CMakeLists.txt를 읽기 때문이다.

```
ISP_Pipeline/
├── .gitignore
├── CMakeLists.txt
├── src/
│   └── check_env.cpp
├── build/      (git 제외)
├── data/       (git 제외)
└── output/     (git 제외)
```

### CMakeLists.txt의 각 구문 이해

| 줄 | 처음 이해 | 정리한 의미 |
| --- | --- | --- |
| `cmake_minimum_required(VERSION 3.16)` | 최소 3.16 필요 | 맞음. 설치된 CMake가 낮으면 에러 |
| `project(ISP_Pipeline CXX)` | 폴더명과 언어 | 언어(CXX = C++)는 맞음. 이름은 폴더명이 아닌 프로젝트 이름표 |
| `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)` | (나중에 추가) | 파일별 컴파일 옵션을 build/compile\_commands.json에 기록. VSCode 헤더 인식용 |
| `set(CMAKE_CXX_STANDARD 17)` | 모름 | `set`은 변수에 값을 넣는 명령. C++17로 컴파일 (`-std=c++17`) |
| `set(CMAKE_CXX_STANDARD_REQUIRED ON)` | 모름 | C++17 미지원이면 옛 버전으로 내려가지 말고 에러. 위 줄을 "필수"로 만듦 |
| `find_package(OpenCV REQUIRED)` | OpenCV 찾기, 필수 | 맞음. 찾으면 `OpenCV_LIBS` 등 변수가 생김 |
| `find_package(PkgConfig REQUIRED)` | PkgConfig 찾기, 필수 | PkgConfig는 라이브러리가 아닌 도구. 다음 줄 명령을 쓸 수 있게 불러옴 |
| `pkg_check_modules(LIBRAW REQUIRED IMPORTED_TARGET libraw)` | pkg-config로 LibRaw 찾기, 필수 | 맞음. `libraw`가 찾을 이름, `LIBRAW`는 결과 이름표, `IMPORTED_TARGET`은 결과를 `PkgConfig::LIBRAW` 묶음으로 만듦 |
| `add_executable(check_env src/check_env.cpp)` | 이 파일을 실행 | 틀림. 이 소스를 컴파일해 `check_env` 실행 파일을 만들라는 정의. 실행은 나중에 직접 |
| `target_link_libraries(check_env PRIVATE ...)` | 라이브러리 위치 지정 | 위치를 넘어 실제로 연결(링크)함. `PkgConfig::LIBRAW`에 헤더 경로도 들어 있음. `PRIVATE`는 이 대상에만 적용, `${...}`는 변수 값 꺼내기 |

OpenCV는 CMake용 설정 파일을 같이 설치해 `find_package`로 바로 찾는다. Ubuntu의 LibRaw는 그 파일이 없어 `pkg-config`로 찾는다. 두 라이브러리를 찾는 방식이 다른 이유다.

### src/check\_env.cpp

```cpp
#include <libraw/libraw.h>
#include <opencv2/core.hpp>
#include <iostream>

int main() {
    std::cout << "LibRaw: " << LibRaw::version() << std::endl;
    std::cout << "OpenCV: " << CV_VERSION << std::endl;
}
```

두 라이브러리를 실제로 include하고 링크해 버전을 출력한다. 설치만이 아니라 코드에서 불러 컴파일까지 되는지 확인하는 용도다.

### 빌드와 실행

```bash
cd build
cmake ..     # CMakeLists.txt를 읽어 빌드 파일 생성
make         # 컴파일과 링크
./check_env  # 실행
```

결과:

```
LibRaw: 0.21.2-Release
OpenCV: 4.6.0
```

cmake 출력에서 `Found OpenCV: /usr`, 컴파일러 `/usr/bin/c++`를 확인했다. conda가 아닌 시스템 설치분을 잡았다는 뜻이다.

## 겪은 문제와 해결

### 1. sudo 비밀번호 분실

- 해결: WSL은 Windows 쪽에서 root로 바로 접속 가능

```powershell
wsl -d Ubuntu-24.04 -u root   # PowerShell에서 root로 접속
```

```bash
passwd suyeon   # 새 비밀번호 설정 (입력이 화면에 안 보이는 게 정상)
exit
```

배포판 이름은 `wsl -l -v`로 확인한다.

### 2. VSCode가 OpenCV 헤더를 못 찾음

- 증상: `cannot open source file "opencv2/core.hpp"` (C/C++ 1696). 빌드는 정상
- 원인: Ubuntu의 OpenCV 4 헤더는 `/usr/include/opencv4/opencv2/` 아래에 있어 기본 경로 `/usr/include`에서 바로 안 보임. CMake는 `find_package`로 경로를 알지만, VSCode 편집기(IntelliSense)는 그 정보를 모름. LibRaw는 `/usr/include/libraw/`라 문제없음
- 확인: `ls /usr/include/opencv4/opencv2/core.hpp`, `pkg-config --cflags opencv4` → `-I/usr/include/opencv4`
- 해결: CMake가 컴파일 정보를 파일로 내보내고, VSCode가 그 파일을 읽게 함
  1. CMakeLists.txt에 `set(CMAKE_EXPORT_COMPILE_COMMANDS ON)` 추가
  2. build에서 `cmake ..` 재실행 → `build/compile_commands.json` 생성
  3. `.vscode/c_cpp_properties.json` 작성

```json
{
    "configurations": [
        {
            "name": "Linux",
            "compileCommands": "${workspaceFolder}/build/compile_commands.json",
            "cppStandard": "c++17"
        }
    ],
    "version": 4
}
```

`includePath`에 `/usr/include/opencv4`를 직접 넣는 방법도 있지만, 라이브러리가 늘 때마다 손으로 추가해야 해서 이 방식을 택했다.

## 질문하며 정리한 개념

### LibRaw는 무엇인가

RAW 파일을 열어 센서 값과 메타데이터를 꺼내주는 라이브러리다. OpenCV `imread`처럼 "파일 여는 담당"이다. RAW는 제조사별 형식(CR2, NEF, ARW, DNG)과 압축, 헤더가 제각각이라 직접 해석하면 그것만으로 별도 프로젝트가 된다. Python rawpy도 내부에서 LibRaw를 쓴다.

| 꺼내는 것 | 쓰는 단계 |
| --- | --- |
| Bayer RAW 배열 | 파이프라인 입력 |
| Bayer 패턴 | Demosaicing |
| Black Level, White Level | 정규화 |
| 카메라 WB 계수 | WB 기준값, Gray World 비교 |
| 색 변환 행렬 | Color Correction |

LibRaw에는 RAW를 완성 사진으로 만드는 전체 처리 기능도 있다. 이번 프로젝트에서는 읽기와 메타데이터 추출만 입력에 쓰고, 전체 처리 기능은 비교용 기준 이미지에만 쓴다. 면접에서는 "LibRaw는 파일 해석에만 쓰고, Black Level 보정부터 감마까지는 직접 구현했다"로 경계를 말한다.

### 라이브러리를 전역에 설치해도 되나

C++에는 Python venv 같은 언어 공식 가상환경이 없다. 리눅스에서는 apt가 헤더를 `/usr/include`, 라이브러리를 `/usr/lib`에 설치하고 컴파일러가 기본으로 거기서 찾는다. 개인 개발에서는 이 방식이 일반적이고, WSL 자체가 Windows와 분리된 환경이기도 하다.

| 분리 방법 | 방식 | 쓰는 때 |
| --- | --- | --- |
| vcpkg / Conan | 프로젝트별 버전을 파일에 적고 프로젝트 안에 설치 | 프로젝트마다 다른 버전, 팀 환경 통일 |
| 소스 빌드 후 지정 경로 설치 | 직접 빌드해 `~/local` 등에 설치 | 특정 버전·옵션 필요 |
| Docker | 컨테이너에 OS째로 환경을 묶음 | 배포, CI, 재현성 |
| conda | conda가 C++ 라이브러리도 제공 | conda 중심 작업. apt 설치분과 섞이면 꼬임 |

이번에는 혼자 하는 1주 프로젝트이고 충돌할 프로젝트가 없어 apt 전역 설치를 택했다. 재현성은 README에 OS와 버전을 적어 챙긴다. 임베디드 장비 개발은 장비 제조사 SDK(크로스 컴파일러와 장비용 라이브러리)로 빌드하는 경우가 많다.

### Visual Studio에서는 왜 CMakeLists가 없었나

Visual Studio는 편집기·컴파일러·빌드 시스템이 한 몸인 IDE라, 프로젝트를 만들면 `.sln`, `.vcxproj`가 자동으로 생겨 CMakeLists.txt 역할을 했다. 프로젝트 속성에서 포함 디렉터리와 링커 종속성을 넣던 것이 지금 `find_package`, `target_link_libraries`가 하는 일이다.

VSCode는 편집기라 빌드 방법을 정해줘야 한다.

| 방법 | 적합한 경우 |
| --- | --- |
| g++ 직접 실행 | 파일 한두 개 테스트 |
| tasks.json | 작은 개인 코드 |
| CMake | 파일이 여러 개이고 라이브러리를 쓰는 프로젝트 |

CMake 없이 한 줄로 빌드하면 다음과 같다. 파일이 늘면 관리가 안 돼 CMake를 택했다.

```bash
g++ -std=c++17 src/check_env.cpp -o check_env $(pkg-config --cflags --libs libraw opencv4)
```

CMake는 Windows·Linux·임베디드에서 같은 파일로 빌드할 수 있어 C++ 업계 표준에 가깝다. 자격요건의 "Linux 기반 개발 환경 사용 경험"과도 연결된다.

### using namespace std를 쓰지 않는 이유

- std의 이름(`min`, `max`, `size`, `data` 등)이 전부 풀려 나와 OpenCV, LibRaw, 내가 만든 이름과 충돌할 수 있다. 충돌하면 에러가 나거나 엉뚱한 쪽이 조용히 선택된다
- `std::vector`, `cv::Mat`처럼 출처가 바로 보인다
- 헤더 파일에는 절대 쓰지 않는다. include하는 모든 파일로 퍼진다
- 파일 하나짜리 코딩테스트에서는 써도 괜찮다. 절충안은 `using std::cout;`처럼 골라 쓰기
- 같은 이유로 `using namespace cv;`도 쓰지 않는다

### .vscode 폴더와 .gitignore

`.vscode`는 터미널에서 `make`로 빌드하는 것만으로는 생기지 않고, VSCode 기능으로 설정을 만들 때 생긴다.

| 파일 | 역할 | 생성 방법 |
| --- | --- | --- |
| c\_cpp\_properties.json | 편집기 헤더 경로 | `C/C++: Edit Configurations (JSON)` 또는 직접 작성 |
| tasks.json | VSCode 안에서 빌드 | `Configure Default Build Task` |
| launch.json | gdb 디버깅 설정 | Run and Debug 패널 |

CMake Tools 익스텐션을 설정 제공자로 쓰면 c\_cpp\_properties.json 없이도 헤더를 인식한다.

`.vscode`는 개인 편집기 설정이라 `.gitignore`에 넣었다. 빌드에 필요한 정보는 CMakeLists.txt에 다 있다. 팀 프로젝트에서는 `extensions.json`, `launch.json`을 공유용으로 올리기도 한다.

최종 .gitignore:

```
# 빌드결과물 및 이미지 데이터 폴더
build/
data/
output/
.vscode/
```

git은 빈 폴더를 추적하지 않아, 새로 clone하면 data와 output 폴더가 없다. README에 생성 방법을 적는다. DNG는 장당 수십 MB이고 FiveK 재배포도 피해야 해서 레포에 올리지 않는다.
